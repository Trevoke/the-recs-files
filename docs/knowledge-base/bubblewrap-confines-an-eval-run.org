#+TITLE: How bubblewrap confines an eval run

Established 2026-10-15 with bubblewrap 0.11.2 on Arch Linux, running pi
0.87.1 with openrouter/qwen/qwen3.7-flash through `evals/providers/pi.js`.
Source: runs.

* An unconfined run can read the whole filesystem
A full eval pass with pi and no sandbox was stopped by the record keeper when
a run began reading the whole filesystem, a RAID array included. The run left
no transcript, so the command is not known.

* A run sees only the system, its harness and its own directory
#+begin_src sh
bwrap --unshare-all --share-net --die-with-parent --clearenv \
  --ro-bind /usr /usr \
  --symlink usr/bin /bin --symlink usr/lib /lib \
  --symlink usr/lib /lib64 --symlink usr/bin /sbin \
  --ro-bind /etc /etc \
  --proc /proc --dev /dev --tmpfs /tmp \
  --bind "$RUN" "$RUN" \
  --ro-bind "$NODE_PREFIX" /opt/node \
  --ro-bind evals/node_modules /opt/evals/node_modules \
  --setenv PATH /opt/node/bin:/usr/bin --setenv HOME "$RUN/home" \
  --setenv OPENROUTER_API_KEY "$OPENROUTER_API_KEY" \
  --chdir "$RUN/project" -- /opt/node/bin/node \
  /opt/evals/node_modules/@earendil-works/pi-coding-agent/dist/bundle/cli.js ...
#+end_src

* A path bound at its own location exposes its parent directories
Binding node and `evals/node_modules` at their real paths made
`/home/stag/src/projects` visible as empty directories. Binding them under
`/opt` leaves `/home` with nothing in it.

* Options read from `--args` keep the environment out of `/proc/<pid>/cmdline`
A process's command line is readable by every user in `/proc/<pid>/cmdline`,
so `--setenv NAME VALUE` on bwrap's command line publishes VALUE, and inside
the sandbox `/proc/1/cmdline` shows bwrap's arguments to the run itself.
`--args FD` makes bwrap "Parse nul-separated arguments from the given file
descriptor" (bwrap(1)); options only, since bwrap 0.11.2 printed its usage
when the command itself came through the descriptor (run). `--clearenv`
unsets "all environment variables, except for PWD and any that are
subsequently set by --setenv" (bwrap(1)), so a run started from an empty
environment with its `--setenv` options on a descriptor sees exactly those
variables and `PWD`. Run 2026-10-19, `evals/providers/common.js` spawning
bwrap with `env: {}` and its options on descriptor 3, a dummy value set as
`CLAUDE_CODE_OAUTH_TOKEN` and `OPENROUTER_API_KEY`, read while the run slept:
#+begin_example
bwrap pid 2422026 cmdline: "bwrap --args 3 -- /usr/bin/sleep 2"
dummy secret in cmdline: false; in bwrap environ: false; bwrap environ bytes: 0
child 2422027 cmdline: "bwrap --args 3 -- /usr/bin/sleep 2"; secret in cmdline: false
#+end_example
Inside the sandbox, `/proc/1/cmdline` read `bwrap --args 3 -- <command>`, and
descriptor 3 was not open in the run's process (`ls -l /proc/self/fd`, run).
`evals/providers/common.test.mjs` checks both, and that `env` inside lists
exactly the variables given and `PWD`. The process that bwrap starts still
holds the variables in its own `/proc/<pid>/environ`, readable by the same
user.
