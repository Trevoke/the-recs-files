#+TITLE: How pi behaves as an eval harness

Established 2026-10-15 against pi 0.87.1, on the rejecting-a-proposed-record
case with anthropic/claude-haiku-5-5 (with skills) and
google/gemini-3-flash-preview (without). Source: runs, and pi's own
docs/skills.md, docs/json.md, docs/security.md, docs/configuration.md.

* A non-interactive run is `pi -p --mode json --no-session`
#+begin_src sh
pi -p --mode json --no-session --model anthropic/claude-haiku-5-5 "$PROMPT"
#+end_src
Stdout is JSONL: a `session` header carrying `cwd`, `tool_execution_start`
(`toolName`, `args`), `tool_execution_end` (`isError`), `message_end` carrying
`usage.cost.total`, and `agent_end` (`messages`). Diagnostics go to stderr.
`--no-session` keeps the run out of `~/.pi/agent/sessions`.

* The JSONL is split on LF only
Node's `readline` also splits on characters inside JSON strings (docs/json.md).

* pi exits 0 when the provider fails
An OpenAI "no credits" error and a Gemini 429 both exited 0. The error is only
in the assistant message: `stopReason: "error"` and `errorMessage` (run).

* A skill load is a `read` of its SKILL.md
pi has no Skill tool. It lists each skill's name, description and path in the
system prompt, and the model loads one by reading the file. On the Haiku run
the first tool call was
`read .../.agents/skills/recs-writing-records/SKILL.md` (docs/skills.md, run).

* Skills are discovered in `.agents/skills` and `.pi/skills`, not `.claude/skills`
Project `.agents/skills` up to the git root, `.pi/skills`, `~/.agents/skills`
and `<agent-dir>/skills` (docs/skills.md).

* In print mode, project skills are skipped silently without `--approve`
Project skills load only under project trust. Without `--approve`, `-p` listed
none of the project's skills and gave no error (run).

* `--no-skills --skill <dir>` loads exactly that directory's skills
`~/.agents/skills` loaded whatever `PI_CODING_AGENT_DIR` was set to.
`--no-skills` removes every discovered skill; `--skill <dir>` still loads an
explicit path beside it, and needs no `--approve` (run).

* A parent directory's AGENTS.md loads, even past a git root
A git repository at `parent/child` loaded `parent/AGENTS.md` as well as its
own (run). Context files need no trust (docs/configuration.md).

* `PI_CODING_AGENT_DIR` moves settings, models and auth
A fresh directory keeps the user's settings.json and models.json out of a run
(run).

* Nothing confines pi to its working directory
Tools are read, bash, edit and write (grep, find and ls off by default), and
none asks for approval. The working directory decides discovery and default
paths, not access (docs/security.md). `--tools` and `--exclude-tools` narrow
the tool set.

* A model is named `<provider>/<id>`
`anthropic/claude-haiku-5-5`, `google/gemini-3-flash-preview`,
`openai/gpt-5.4-mini` (run). A model missing from pi's catalog prints "Using
custom model id" and runs. OpenRouter models are `openrouter/<vendor>/<model>`
with `OPENROUTER_API_KEY`; `openrouter/anthropic/claude-sonnet-5.5`,
`openrouter/openai/gpt-5.5`, `openrouter/google/gemini-3.1-pro-preview` and
`openrouter/qwen/qwen3.7-max` ran (run).

* pi's cost for a model missing from its catalog is not the provider's price
The anthropic/claude-haiku-5-5 run (custom model id) reported
`usage.cost.total` summing to $0.18 for about 2,300 output tokens, 37,000
cache reads and 17,000 cache writes. At OpenRouter's listed price for
claude-haiku-5.5 ($0.10 per million input tokens, $0.50 per million output)
that is a few cents at most (run; OpenRouter `/api/v1/models`).

* promptfoo 0.124.1 has no pi provider
None in `dist/src/providers` (grep).

* A model may read a skill through bash instead of `read`
In a sandboxed run, claude-sonnet-5.5 (through OpenRouter) read
`.agents/skills/recs-writing-records/SKILL.md` with
`cat ... | head -80` in a bash call, and never called `read` on a skill
(run, 2026-10-15).

* Gemini through OpenRouter sometimes ends a run with "The operation was aborted"
Two runs of openrouter/google/gemini-3.1-pro-preview stopped after a tool
call, the next assistant message carrying `stopReason: "error"`,
`errorMessage: "The operation was aborted"` and no output tokens; another
stopped with "JSON error injected into SSE stream". Rerunning the same case
ran to the end (runs, 2026-10-15).

* Gemini through OpenRouter sometimes ends its turn empty after reading a skill
In two runs of openrouter/google/gemini-3.1-pro-preview, on
proposing-a-record and rejecting-a-proposed-record, the only tool call was a
`read` of `recs-writing-records/SKILL.md`, and the next assistant message had
`stopReason: "stop"` and no text. pi exited 0 and the run left the fixture
untouched (runs, 2026-10-15).

* promptfoo's scheduler drops a run that waits 300 s for its provider
promptfoo 0.124.1 queues calls per provider id, lowers that provider's
concurrency when it is rate limited, and rejects a call that has waited
`PROMPTFOO_SCHEDULER_QUEUE_TIMEOUT_MS` (300000 by default): "Request
pi:openrouter/google/gemini-3.1-pro-preview-... timed out after 300000ms in
queue". Gemini kickstart runs, several minutes each at `-j 6`, lost three runs
this way. `PROMPTFOO_DISABLE_ADAPTIVE_SCHEDULER=true` removes the queue and the
back-off with it: the same six runs all failed on OpenRouter's 429 "Rate limit
exceeded: new-account-rpm/google/gemini-3.1-pro-preview" (`dist/src/shared-*.js`,
`RateLimitRegistry`; runs, 2026-10-15).

* An explicit `-e` extension loads under `--no-extensions`
`--no-extensions` turns off discovery only; an extension named with `-e`
still loads beside it (pi 0.87.1, `--help`, 2026-10-19).
#+begin_src sh
node evals/node_modules/@earendil-works/pi-coding-agent/dist/bundle/cli.js --help | grep -E 'no-extensions|--extension'
#+end_src
#+begin_example
  --extension, -e <path>         Load an extension file (can be used multiple times)
  --no-extensions, -ne           Disable extension discovery (explicit -e paths still work)
#+end_example

* A print-mode run discovers `<agent-dir>/skills` without `--approve`
Auto-discovery adds `<agent-dir>/skills` (the directory
`PI_CODING_AGENT_DIR` names) and `$HOME/.agents/skills` as user skills,
outside the project-trust check that gates a project's `.agents/skills`
and `.pi/skills`. Read from pi 0.87.1's source, with no run:
`dist/core/package-manager.js:713` (`globalBaseDir = this.agentDir`),
`:1966` (`skills: join(globalBaseDir, "skills")`), `:1976` (`$HOME/.agents/skills`),
`:1978` (project skill directories only when `projectTrusted`), and `:2010`
and `:2017`, which add both user directories unconditionally. The bundle in
`dist/bundle/chunks/` carries the same code.

* A tool's `usage` reaches the JSONL on its `tool_execution_end`
A tool's result may carry a `usage`; `tool_execution_end` carries the whole
result as `result`, so the JSONL has it at `result.usage.cost.total`. Read
from pi 0.87.1's source, with no run: `pi-agent-core/dist/agent-loop.js:588`
keeps `usage` on the result, `:611-617` emits it as `result`, and
`pi-coding-agent/dist/modes/json-event.js:17-18` writes every event but
`message_update` unchanged.

* `pi install -l <path>` records the path in `.pi/settings.json` and copies nothing
A project-scoped install of a local path appends that path, relative to the
project's `.pi`, to `packages` in `<project>/.pi/settings.json`; it checks
that the path exists and does nothing else, so it needs no network. Read from
pi 0.87.1's source: `dist/package-manager-cli.js:825` (`installAndPersist`
with `local`), `dist/core/package-manager.js:777-783` (a local source is only
checked for existence), `:787-790` and `:618-646` (the source added to the
project's `packages`), `:1138-1146` and `:1785-1788` (the path made relative
to `<cwd>/.pi`), `dist/core/settings-manager.js:62` (the project settings
file). A first install needs no `--approve`: before `.pi/settings.json`
exists the project has nothing that asks for trust
(`dist/core/project-trust.js:21-23`, `dist/core/trust-manager.js:8-16`);
once it exists, a second install without trust stops with "Project is not
trusted. Use --approve to modify local package config."
(`dist/package-manager-cli.js:809-810`). Run in bubblewrap with no network
namespace shared, 2026-10-19:
#+begin_src sh
pi install -l ./.pi/the-recs-files-pi
cat .pi/settings.json
#+end_src
#+begin_example
Installing ./.pi/the-recs-files-pi...
Installed ./.pi/the-recs-files-pi
{
  "packages": [
    "the-recs-files-pi"
  ]
}
#+end_example

* A project package loads only under project trust
`.pi/settings.json` is a project resource that asks for trust
(`dist/core/trust-manager.js:8-16`, `:150-169`), and an untrusted project's
settings load as empty, so its `packages` are never read
(`dist/core/settings-manager.js:195-198`). In a run with no UI and no saved
decision, trust defaults to no, silently (`dist/core/project-trust.js:37-51`,
`dist/main.js:578-585`). Run in bubblewrap, 2026-10-19, after the install
above: `pi --mode rpc` answered `get_commands` with no `skill:` entry, and with
`--approve` with all thirteen `skill:recs-*` entries, each with
`"scope":"project","origin":"package"`.

* `<agent-dir>/trust.json` keeps a project trust decision; `--approve` lasts one run
`--approve` sets a per-run override that is returned before any stored
decision and never written (`dist/cli/args.js:215-216`,
`dist/core/project-trust.js:18-19`, `dist/main.js:584`, `:599`). A stored
decision lives in `trust.json` in the agent directory, keyed by the
canonical project path, a parent's entry covering its children
(`dist/core/trust-manager.js:20-33`, `:170-200`). A run with no `--approve`
whose project asks for trust resolves it through `resolveProjectTrusted`
(`dist/main.js:580-583`, `:595-600`), which reads `trust.json`
(`dist/core/project-trust.js:37-40`); pi writes it when a person answers
"Trust" at the interactive prompt (`dist/core/project-trust.js:52-55`).
A pi started with no flags, with the same `PI_CODING_AGENT_DIR`, is therefore
trusted. The recs files' subagent extension starts its child pi with
`--mode json -p --no-session` and at most `--model` and `--thinking`, in the
parent's working directory, and passes no `env`, so the child inherits the
parent's environment (`packaging/pi/extensions/subagent/index.ts:41-43`,
`:67`): a parent's `--approve` does not reach the child, and `trust.json`,
found through the inherited `PI_CODING_AGENT_DIR`, does. Run in bubblewrap,
2026-10-19: after `--approve` runs the agent directory held no `trust.json`;
with `trust.json` holding `{"<project>": true}`, a run with no flags loaded
the package's thirteen skills and its `subagent` extension, the extension
registering the `subagent` tool, with no load error (pi's
`DefaultResourceLoader`, run inside the sandbox).

* `--no-skills` and `--no-extensions` drop a package's skills and extensions
Each keeps only paths named on the command line, and a package's resources
are not among them (`dist/core/resource-loader.js:316-318`, `:330-332`). Run
in bubblewrap, 2026-10-19: with the project trusted, `DefaultResourceLoader`
with `noSkills` and `noExtensions` loaded no skill and no extension.

* `.git/info/exclude` hides a path from `git status`, `git add -A` and `git ls-files --others --exclude-standard`
It holds patterns in the form of `.gitignore` that apply to one repository and
are not committed (gitignore(5)). An excluded untracked path is absent from
`git status --porcelain` and from `git ls-files --others --exclude-standard`,
and `git add -A` does not add it (run, 2026-10-19).

* An rpc `get_commands` lists the skills a run loads, with no model reached
`pi --mode rpc --no-session --offline`, given `{"type":"get_commands"}` on
stdin, answers with every extension command, prompt template and skill the
run loaded, each skill as `skill:<name>` with its `sourceInfo`, and exits
when stdin closes; it needs no API key (`dist/modes/rpc/rpc-mode.js:542-569`).
`packaging/validate.sh` counts the `skill:recs-*` entries this way to check a
user-scope install. Run in bubblewrap with `OPENROUTER_API_KEY` empty,
2026-10-19, in a project with the pi package installed at project scope and
trusted:
#+begin_src sh
echo '{"type":"get_commands"}' | pi --mode rpc --no-session --offline | grep -o '"skill:recs-[a-z-]*"' | wc -l
#+end_src
#+begin_example
13
#+end_example

* pi's bash tool inherits pi's whole environment, `OPENROUTER_API_KEY` included
pi's bash tool runs each command with `env ?? getShellEnv()`
(`dist/core/tools/bash.js:53`, `:123`), and `getShellEnv` returns
`{...process.env}` with pi's bin directory added to `PATH`
(`dist/utils/shell.js:115-123`); only the `PI_*` session variables are
replaced (`dist/core/tools/bash.js:124-140`). Nothing in pi 0.87.1's `dist/`
scrubs a subprocess's environment (grep for `scrub`, `sanitizeEnv`: no
match). An agent told to run `env` in a sandboxed run listed
`OPENROUTER_API_KEY` among its variables
(bubblewrap-confines-an-eval-run.org: A run sees only the system, its harness
and its own directory).
