SKILLS FOR CODING AGENTS · 1.0.0-BETA

Keep a system's decisions in records, and build from them.

The recs files are skills for coding agents. The agent keeps each decision about your system as a short, numbered record, and writes the code from those records. The records persist between sessions; the agent's context does not.

01Congruence

Each change brings the code and the records into closer agreement.

Agents write code faster than anyone documents it, and the reasons behind it are the first thing lost. The recs files store those reasons as records. When a new record contradicts existing sentences, in other records, in skills or in code, the agent finds each one, proposes its replacement, and lands the record and the replacements in a single commit.

1
The agent drafts the record and finds every sentence it makes false.
2
The record keeper reviews the draft alongside the proposed replacements, and approves.
3
The record and its replacements land in one commit. Records and code agree again.
02Events and state

A record is an event. A projection is the current state.

If you know event sourcing, you know this shape. Records are appended in order and never rewritten in substance; a new decision on the same question is a new record that supersedes the old one. Fold the records of one category and you get its projection: the titles of every active record. The projection is what the agent reads.

03Context

The agent reads every title, then opens only the records the task needs.

A projection costs one line per record, so the agent can read all of it at the start of a task. From the titles it picks the records that bear on the work and opens those files, and only those. Context goes to the decisions in play, at the depth each one needs.

04Inverted pyramid

The most important information comes first, at every level.

Newspapers write in an inverted pyramid: the headline, then the essential facts, then the detail. A reader can stop at any point and still have the story.

Records follow the same structure. A record's title states its decision, so a reader who stops at the projection already knows the substance. The record file holds the detail, and the knowledge base holds the sources the idea came from.

05Use cases

Work starts from what a person is trying to achieve.

User workflows follow Alistair Cockburn's use cases. Each states one actor's goal, a main success scenario in numbered steps, and extensions keyed to the steps where things can go differently. Each also states two guarantees: what holds even when the workflow fails, and what the actor gets when it succeeds.

06Hub and spokes

Records connect as hubs and spokes, with the user workflow at the center.

The vision states what the system is for, and the ubiquitous language defines the words of its domain. Each user workflow is a hub: it names the features it reaches, the messages its actor can meet, and the terms it uses. Start from a workflow, follow its references, and you have what the system does for that goal.

07Example: a lending library

One goal, traced from the actor to the test.

A borrower wants to keep a book longer. These are the records that govern the renewal, and the code and test that cite them.

User workflow · Actor: borrower

UW-3 Renew a loan

Main success scenario
  1. Borrower asks to renew a loan
  2. Library renews it (F-12: A borrower can renew a loan) and shows the new due date
Extensions

2a. The book is reserved

Library refuses with MSG-4: A reserved book cannot be renewed; the use case ends

2b. The loan is overdue beyond the grace period

Library refuses with MSG-5: An overdue loan cannot be renewed; the use case ends

Feature · EARS

F-12 A borrower can renew a loan

  1. When a borrower renews a loan, the library shall set the loan's due date one loan period after the renewal date.
  2. If the book is reserved, then the library shall refuse the renewal with MSG-4: A reserved book cannot be renewed.
  3. While a loan is overdue beyond the grace period, the library shall refuse any renewal of it with MSG-5: An overdue loan cannot be renewed.
  4. Where the library sets a renewal limit, the library shall refuse a renewal past it with MSG-6: This loan has reached its renewal limit.
The code cites the requirement
# F-12 §2: A borrower can renew a loan
return refuse(:msg_4) if loan.book.reserved?

# F-12 §1: A borrower can renew a loan
loan.due_on = Date.today + loan.period
The test asserts the message catalog's text
# F-12 §2: A borrower can renew a loan
assert_equal "A reserved book cannot be renewed",
             renew(reserved_loan).message
